# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Mods Config VR (`ModsConfigVR`) is a **C++23 DLL plugin** for F4SE (Fallout 4 Script Extender) for Fallout 4 VR, built on the [F4VR Common Framework](external/F4VR-CommonFramework/README.md).

It is a shared in-game configuration menu for Fallout 4 VR mods. A mod ships a declarative JSON config spec or already has an MCM menu, and the player edits the mod's real settings in VR. A change of every mod waits for an explicit Save, and a mod that registers through the native API gets live preview. The design is in [docs/design/](docs/design/README.md). So far the menu opens on its front page and lists the MCM mods that are installed. Its title bar has Help, which shows a page of the menu's controls with the player's buttons, and Minimize and Close, as the wrist has. A mod that is selected shows its pages in the tree and their rows, and a config spec's page that is selected shows the pages under it, a level further in, with a breadcrumb for each. A row of a group is shown while the setting that controls the group is on. A switcher, a slider, a stepper and a dropdown that are kept in a global of the game, in a ModSetting or in a property of a script are edited, and so is a dropdown of the files of a folder, a stepper and a dropdown have the options of a FormList or of a property of a script, which are read in the game, a ModSetting has a Reset to the default of its mod, a button calls the function of a script, and so does a row whose value is set, with the value, a text input is typed on SteamVR's keyboard, a config spec's controller binding of a CommonFramework mod is shown as its icons and its sentence and is built from its parts in its editor, a hotkey shows the key MCM has for it, read-only, and a control the menu does not have is its text and its type, with a help that says so. A config spec is read too, with its pages, its sections, which nest and fold, its settings, a read-only one among them, with how a number is shown, its choices, with their shared lists and their options from the game, its texts, spacers and images, its buttons, which call the function of a script or run a console command, with the text on their button, and the conditions a row is shown and enabled by, and the warnings a setting and a button tell while theirs holds, and the mod ships its own config spec for its TOML. A config spec's values are read from its TOML and INI files, its globals and its properties of scripts as its mod is selected, and a change waits for a Save: the footer counts the unsaved changes, and has Save, which writes them into the files and then the game, or nothing where one cannot be written, and creates a file that is not there, and runs the action of each setting it wrote, and Discard, which takes them back. A value the player types that is no value of its setting is invalid, as one of a file is, and Save is disabled while one is. A `live` global or property is in the game as it is changed, until Discard puts it back. A setting's Reset sets the config spec's default, which waits for a Save too. A config spec's setting says when its change takes effect, which the help line has in a tag while it is pending, and is unknown, with no tag, where nothing says it, as for every MCM setting: the status after a Save that wrote one that takes effect after a restart says so, and so does the menu's front page until the game is restarted. A config spec's problems are in the log, and with the Developer tools of the menu's own settings on, its front page lists each config spec's errors and warnings, and a config spec's report reads it from a live copy of its spec.json, which is read again each time it is saved. The framework work the mod needed first is listed in [docs/design/framework-requirements.md](docs/design/framework-requirements.md), and its commits are tracked in [docs/design/framework-plan.md](docs/design/framework-plan.md). The mod's own milestones are in [docs/design/mod-plan.md](docs/design/mod-plan.md), and the commits of each in the file of its phase, `docs/design/mod-plan-phase-<n>.md`.

## Build System

**Prerequisites:**

- `VCPKG_ROOT` environment variable pointing to a vcpkg installation
- Visual Studio 2022 or 2026 (MSVC toolchain, x64)
- CMake 4.2+
- Git submodules initialized: `git submodule update --init --recursive`

**Configure and build:**

```bash
cmake --preset default                                    # uses VS 2026; substitute vs2022 preset if needed
cmake --build --preset release                            # or: cmake --build build --config Release
cmake --build --preset debug                              # or: cmake --build build --config Debug
cmake --build --preset tracy                              # Release + the Tracy profiler client
```

The default preset inherits `cmake-dev + vcpkg + windows + vs2026`. The `release` / `debug` / `package` / `tracy` build presets build the `default` configure preset. The build output is `build/`. In-source builds are blocked.

**Auto-copy to game (optional):** `CMakeUserPresets.json` (git-ignored, start from `CMakeUserPresets.json.template`) defines a `custom` preset that sets `POST_BUILD_COPY_PLUGIN` and `COPY_PLUGIN_BASE_PATH` to copy the DLL and PDB to `<path>/F4SE/Plugins/` on each build. Multiple paths can be separated by `;`. `COPY_PLUGIN_CONFIGURATIONS` limits the copy to some build configurations: `all` (default) or a `;` list like `Release` / `Debug;RelWithDebInfo`.

**Packaging:** an explicit step, not part of a normal build — build the `package_mod` target (`cmake --build --preset package`, or `cmake --build build --config Release --target package_mod`), which builds the plugin if needed and runs `cmake/package.cmake` to produce a versioned `.7z` with the DLL and the `data/mod/` files in `build/package/`. A non-Release archive has the configuration in its file name. It also packs the shared `data/showcase/` game `Data` tree, containing both the MCM and config spec showcases, into one optional Showcase `.7z` for developers.

**Unit tests:** code that does not need the running game (the settings model, the loaders) is unit tested with Catch2, in [tests/](tests/CMakeLists.txt). A normal build also builds `ModsConfigVR_tests`; run them with `ctest --test-dir build -C Release --output-on-failure`, or one with `build/tests/Release/ModsConfigVR_tests "<test name>"`.

- The executable compiles the sources it covers, listed in `tests/CMakeLists.txt`, and links the framework and CommonLibF4 as the mod does. `tests/Setup.cpp` sets CommonLibF4's `REL::NO_GAME`, so there is no game in the process: a test that calls the game fails with an access violation.
- A new source under test is added to that list, with its `<Name>Tests.cpp`.
- `tests/TestSwf.h` builds an SWF file in memory, for a test of an image.
- `tests/TestGlobals.cpp` is the tests' own `getGlobal` and `setGlobal`, linked in place of the mod's `GameGlobals.cpp`: it has globals in a map in place of the game's, which a test fills with a `TestGlobals`, for a test of a store, of a condition and of a row that is pressed. The map is kept from test to test: a test that reads a global has a `TestGlobals`, which starts with none. `tests/TestProperties.cpp` is the tests' own `getProperty`, `setProperty` and `getOptionTexts` in the same way, linked in place of the mod's `GameProperties.cpp`: a test fills its properties of scripts, and the lists a choice reads its options from, with a `TestProperties`. A test of a ModSetting writes MCM's files in a folder of its own (`tests/TestFiles.h`, whose `ReadOnly` makes a file that cannot be written), MCM is not called in a test, which has no game. `tests/TestEvents.cpp` is the tests' own `mcm::sendEvent` and `mcm::sendPauseMenuEvents`, linked in place of the mod's `McmEvents.cpp`: it keeps the events the MCM store sends, which a test reads with a `TestEvents`. A source that sends an event needs no more than that. `tests/TestActions.cpp` is the tests' own `callFunction`, `runConsoleCommand`, `openWebLink` and `sendSavedMessage`, linked in place of the mod's `GameActions.cpp`: it keeps the functions a store calls, the console commands it runs and the F4SE messages of its Saves, which a test reads with a `TestActions`.
- `tests/FullPanelTests.cpp` checks what the panel does: what is selected, and what a press of the pointer on a row of the tree or on a breadcrumb selects. It draws the panel in frames of ImGui with no game and no renderer, which `tests/TestPanel.h` sets up as the framework's canvas does.
- `tests/FullPanelRenderTests.cpp` draws the panel the same way and saves it as images, to look at a change of the UI before it is tried in the headset. They check nothing and are not run by `ctest`: run `build/tests/Release/ModsConfigVR_tests "[render]"`, and open the `.bmp` files in `build/tests/render/`. Add a case there for a new view or state of the panel. One case draws every page of the MCM showcase, and one every page of the config spec showcase. An image of a page is drawn from its pixels, as the game draws it from its texture, and a config spec's texture from the config spec showcase's DDS file of it.
- `-DMODS_CONFIG_BUILD_TESTS=OFF` leaves them out.

Everything else is tested by hand, in the game.

**CI:** `.github/workflows/build.yml` configures and builds Release on every push and pull request to `main`, and runs the unit tests. `.github/workflows/maintenance.yml` runs pre-commit there and commits any fixes back to the branch (pull requests from forks are only checked).

## Code Style

clang-format enforces style (`.clang-format`): LLVM-based, 180-column limit, 4-space indent, CRLF line endings, pointer-left (`T* p`), namespace indentation enabled, braces on new lines for classes/functions/namespaces.

After editing code run `pre-commit run --files <changed files>`: it formats `src/` and `tests/` with clang-format and runs the repo's other checks (`.pre-commit-config.yaml`). `data/` and `external/` are excluded.

After cloning, run `pre-commit install` once to run those checks on every commit; the hook lives in `.git/hooks/` and is not version-controlled.

Conventions:

- **Naming:** camelCase for variables/functions, PascalCase for types/classes
- **Namespace:** all project code lives in `namespace mods_config`
- **Logging:** spdlog throughout; use `logger::trace/debug/info/warn/error` from the framework
- **C++ standard:** C++23; use modern features (ranges, constexpr, smart pointers, structured bindings)
- **PCH:** [src/PCH.h](src/PCH.h) is the precompiled header — add widely-used includes there

## Architecture

### Plugin Lifecycle

The entry point is [src/ModsConfigVR.h](src/ModsConfigVR.h) / [src/ModsConfigVR.cpp](src/ModsConfigVR.cpp), a `ModBase` subclass (global `g_modsConfig`) that implements the F4SE plugin hooks:

- `F4SEPlugin_Query` / `F4SEPlugin_Load` — standard F4SE registration, forwarded to the framework
- `onModLoaded()` — F4SE load phase; register Papyrus functions and install hooks
- `onGameLoaded()` — once, when the game finishes loading
- `onGameSessionLoaded()` — on a new game and on every save load
- `onFrameUpdate()` — every frame while the player is loaded

### Config

[data/config/ModsConfigVR.toml](data/config/ModsConfigVR.toml) is the shipped default config, in TOML. It is embedded in the DLL (resource `IDR_CONFIG`) and written on first run to `%USERPROFILE%\Documents\My Games\Fallout4VR\Mods_Config\ModsConfigVR\ModsConfigVR.toml`. A player's `ModsConfigVR.ini` from an older version is moved into it by the framework, with its values, on the first load that finds no TOML.

- The main section is `[ModsConfigVR]`; it must match `NAME` in `CMakeLists.txt`, which the config reads back as both the file name and the default section. It holds the binding that opens the menu, and the Back button: a short press of a button of the hand that points at the panel, and not a binding. As shipped it is the grip, which also moves the panel: the panel then moves only when the grip is held longer (`UIManager::setWorldMoveHoldDelay`).
- `[Panel]` holds the menu's panel in the world: its scale, which is the size of its text and rows, its distance, height and tilt, the opacity of its background, the button that moves it and how smoothly it follows the hand, the gesture that puts it in front of the player again, and the distance at which that happens by itself.
- `[Developer]` holds the Developer tools, for a config spec's author: whether they are on, which config specs the menu's front page lists (`attention`, `all` or `one`), the config spec `one` lists by its modName, and whether the front page's section is folded. The front page writes the filter and the fold at once, with `Config::saveDeveloper`.
- `[Pointer]` holds the menu's pointer: where the ray is on the hand, how the ray and the mark on the panel look, and how fast the thumbstick scrolls. It is read into an `imgui::PointerStyle` and given to the framework's pointer every frame. It also holds the pulse the hand that points gets as its press does something in the panel.
- `[Debug]` holds the framework's keys (log level and pattern, flow flags, data dumps, debug draw).
- To add a value: a member in `Config.h`, a read in `Config::loadConfigInternal()` (`config[SECTION]["key"].value_or(default)`, which gives the default for a key that is missing or of another type), and the key in the shipped file. Write a float with a decimal point (`1.0`) and a string in quotes.
- `ConfigBase` watches the file and reloads it on change, so edits apply while the game runs. The reload runs on the watcher's thread: apply anything that calls into the engine from `onFrameUpdate()`.
- Bump `iVersion` in `[Debug]` when the shipped file changes, so existing users' files are migrated. A value whose type or name changes is moved in `updateConfigToLatestVersionCustom`.

### Mod Data

The mod's VR UI is mostly one Dear ImGui panel in a `vrui` layout (`imgui::UIImGuiPanel`), with the framework's primitive-drawn `vrui` panel buttons where a control sits on the hand; see [docs/design/ui-and-vr-interaction.md](docs/design/ui-and-vr-interaction.md). Its look (colors, type, sizes, the ImGui style, and mocks of each panel) is the design system in [docs/design/design-system/](docs/design/design-system/README.md), which is also published as an artifact: its README says how to change and publish it. [src/Theme.h](src/Theme.h), the colors, sizes and `applyStyle` for ImGui, is generated from it by `docs/design/design-system/tools/gen_theme.py`: change the tokens, not the header. It does not use NIF button atlases: the template's `ui-common` / `ui-example` atlases and their source PNGs were removed on purpose.

`data/mod/` is the mod's game `Data` tree, packaged beside the DLL. `Meshes\ModsConfigVR\f4cf\` and `Textures\ModsConfigVR\f4cf\` hold the framework's own assets (activation sphere, binding icons, shared VR UI icons): ship them as they came and refresh them from `external/F4VR-CommonFramework/mod-template/` when updating the framework. The mod's own assets go beside them.

`data/mod/ModsConfigVR/Config/ModsConfigVR/spec.json` is the mod's own config spec, which edits its TOML. A unit test checks that each of its settings is a key of the shipped TOML, with the shipped value as its default: change the config spec with the TOML.

`data/showcase/ModsConfigVR/Config/ModsConfigVR_Showcase/` is the config spec showcase, "Mods Config VR: Showcase", in the shared showcase game `Data` tree: a config spec with what a config spec has, one kind a page, and what a config spec can get wrong on its Mistakes page. Its front page has its banner, an image of `data/showcase/Textures/ModsConfigVR_Showcase/`, and its page Most Used a row of each kind a mod uses most, with sections that nest and a setting that shows them. Its page Detailed Examples has the pages of one kind each. Its values are in a TOML file and an INI file beside its `spec.json`, and a setting of its page Files is in a file of `My Games` that is not shipped. Its page Warnings has rows whose warnings hold as it is shipped, and one that is invalid too, in `invalid.toml`. Its page Files also has a section of that shipped TOML file, `invalid.toml`, whose values are not the ones of their settings, as the menu shows a value that is invalid. Its textures are in `data/showcase/Textures/ModsConfigVR_Showcase/`, DDS files that are not compressed, written by `tools/gen_config_spec_showcase_textures.py` with the pictures of the MCM showcase: change an image there and run it again. Install it in the game to try a change of a config spec in the headset, and add to it what a new commit reads or draws. A unit test loads it and checks that its TOML has the default of each setting, and a render test draws each of its pages (`config-spec-showcase-*.bmp`).

`data/showcase/MCM/Config/ModsConfigVR_McmShowcase/` is the MCM showcase in the same game `Data` tree: an MCM config with every kind of row an MCM config has, in every look, one kind a page. It has only what works in MCM too: the config spec showcase demonstrates what the config spec schema adds to MCM. It shows how an MCM menu looks in the mod, and ships with the config spec showcase in one optional archive for developers. Install it in the game to try a change of a row in the headset, and add to it what a new commit draws: a control, a state, an edge case. A unit test loads it, and a render test draws each of its pages (`mcm-showcase-*.bmp`). Its `keybinds.json` has the hotkeys of its hotkey rows, as MCM needs it to bind a key to one. Its `lib.swf` holds the images of its "Images" page, and is written by `tools/gen_mcm_showcase_lib.py`: change an image there and run it again.
